## 1. 多 Channel 管理总览

### 1.1 为什么需要多 Channel？

```
┌─────────────────────────────────────────────────────────┐
│              多 Channel 管理的价值                        │
├─────────────────────────────────────────────────────────┤
│                                                         │

│  ❌ 只能在一个平台使用                                  │
│  ❌ 消息无法互通                                        │
│  ❌ 切换平台麻烦                                        │
│  ❌ 重要消息可能遗漏                                    │
│                                                         │
│  多 Channel 的优势：                                    │
```

## 2. 多 Channel 配置

### 2.1 配置文件结构

```json
// ~/.openclaw/config.json

{
  "channels": [
    {
      "type": "feishu",
      "appId": "cli_xxxxxxxxxx",
      "appSecret": "xxxxxxxxxxxxxxxx",
      "enabled": true,
      "name": "飞书 - 工作渠道",
      "priority": "high"
    },
    {
      "type": "telegram",
      "botToken": "123456:ABC-DEF1234...",
      "enabled": true,
      "name": "Telegram-个人渠道",
      "priority": "normal"
    },
    {
      "type": "discord",
      "botToken": "xxxxxxxxxxxxxxxxxxxx",
      "guildId": "123456789...",
      "channelId": "987654321...",
      "enabled": false,
      "name": "Discord-备用渠道",
      "priority": "low"
    }
  ],
  
  "channelConfig": {
    "defaultChannel": "feishu",
    "fallbackEnabled": true,
    "syncEnabled": true
  }
}
```

### 2.2 Channel 配置参数

| 参数 | 说明 | 必填 | 示例 |
|------|------|------|------|
| `type` | 渠道类型 | 是 | feishu/telegram/discord |
| `enabled` | 是否启用 | 是 | true/false |
| `name` | 渠道名称 | 否 | "飞书 - 工作" |
| `priority` | 优先级 | 否 | high/normal/low |
| 其他参数 | 根据 type 不同 | 是 | 见各渠道配置指南 |

### 2.3 配置多个 Channel

**步骤 1：准备各渠道凭证**

```
飞书：
- App ID: cli_xxxxxxxxxx
- App Secret: xxxxxxxxxxxxxxxx

Telegram:
- Bot Token: 123456:ABC-DEF1234...

- Bot Token: xxxxxxxxxxxxxxxxxxxx

- Channel ID: 987654321...
```

**步骤 2：编辑配置文件**

```bash

```

```json
{

    {
      "type": "feishu",

}
```

**步骤 4：重启 Gateway**

```bash

```

## 3. 消息路由

### 3.1 什么是消息路由？

```
消息路由 = 智能决定消息从哪个渠道发送

场景示例：

你：（在飞书发送消息）
  ↓
OpenClaw 接收
  ↓
根据规则决定回复渠道
  ↓
从飞书回复（同一渠道）

或者：

重要通知
  ↓
根据配置决定推送渠道
  ↓
同时从飞书 + Telegram 发送
```

### 3.2 路由规则配置

```json
{
  "routing": {
    "rules": [
      {
        "name": "工作消息走飞书",
        "condition": {
          "timeRange": "09:00-18:00",
          "dayOfWeek": "1-5"
        },
        "channel": "feishu"
      },
      {
        "name": "非工作时间走 Telegram",
        "condition": {
          "timeRange": "18:00-09:00",
          "dayOfWeek": "1-7"
        },
        "channel": "telegram"
      },
      {
        "name": "紧急消息多渠道",
        "condition": {
          "priority": "urgent"
        },
        "channels": ["feishu", "telegram", "discord"]
      }
    ],
    "defaultChannel": "feishu",
    "fallbackChannel": "telegram"
  }
}
```

### 3.3 路由优先级

```
┌─────────────────────────────────────────────────────────┐
│              消息路由优先级                              │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  1. 用户指定渠道                                        │
│     "用 Telegram 发给我" → 走 Telegram                  │
│                                                         │
│  2. 路由规则匹配                                        │
│     工作时间 → 飞书                                     │
│     非工作时间 → Telegram                              │
│                                                         │
│  3. 消息来源渠道（默认）                                │
│     从飞书发来 → 回复飞书                               │
│     从 Telegram 发来 → 回复 Telegram                    │
│                                                         │
│  4. 默认渠道                                            │
│     以上都不匹配 → 使用 defaultChannel                  │
│                                                         │
│  5. 备用渠道                                            │
│     默认渠道失败 → 使用 fallbackChannel                 │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

## 4. 跨平台消息同步

### 4.1 什么是消息同步？

```
消息同步 = 让不同渠道的消息保持一致

场景：
你在飞书收到通知
同时 Telegram 也收到相同通知
确保两边内容一致

好处：
• 不会遗漏重要消息
• 多设备查看一致信息
• 重要通知多重保障
```

### 4.2 同步配置

```json
{
  "sync": {
    "enabled": true,
    "channels": ["feishu", "telegram"],
    "syncTypes": {
      "notifications": true,
      "reminders": true,
      "reports": true,
      "alerts": true
    },
    "excludeTypes": ["casual_chat"],
    "delaySeconds": 0
  }
}
```

### 4.3 同步策略

```
┌─────────────────────────────────────────────────────────┐
│              消息同步策略                                │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  全量同步：                                             │
│  • 所有消息都同步到所有渠道                             │
│  • 优点：信息完整                                       │
│  • 缺点：可能消息过多                                   │
│                                                         │
│  选择性同步：                                           │
│  • 只同步重要消息                                       │
│  • 优点：减少干扰                                       │
│  • 缺点：可能遗漏                                       │
│                                                         │
│  智能同步：                                             │
│  • 根据消息类型、时间、用户偏好决定                     │
│  • 优点：平衡完整性和干扰                               │
│  • 缺点：配置复杂                                       │
│                                                         │
│  推荐：智能同步                                         │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

### 4.4 同步示例

```
场景：日报推送

配置：
{
  "sync": {
    "enabled": true,
    "channels": ["feishu", "telegram"],
    "types": ["daily_report"]
  }
}

效果：
每天 18:00
├─ 飞书：发送日报 ✅
└─ Telegram: 发送日报 ✅

两边内容一致，用户可以在任意渠道查看。
```

## 8. 最佳实践

### 8.1 Channel 选择原则

```
✅ 推荐做法：

1. 主备搭配
   • 至少配置 2 个 Channel
   • 一个主用，一个备用
   • 主用故障时自动切换

2. 场景分离
   • 工作用企业 IM（飞书/Slack）
   • 个人用即时通讯（Telegram/微信）
   • 根据场景选择合适渠道

3. 优先级设置
   • 重要通知：高优先级渠道
   • 常规通知：普通优先级
   • 休闲内容：低优先级

4. 定期测试
   • 每周测试各 Channel 连通性
   • 确保备用 Channel 可用
   • 及时更新凭证
```

### 8.2 消息同步原则

```
✅ 推荐做法：

1. 避免过度同步
   • 只同步重要消息
   • 避免消息轰炸
   • 尊重用户偏好

2. 格式适配
   • 不同渠道可能有格式限制
   • 自动调整消息格式
   • 保持内容一致

3. 去重处理
   • 避免重复消息
   • 使用消息 ID 去重
   • 设置合理时间窗口

4. 隐私保护
   • 敏感信息不同步
   • 遵守各平台隐私政策
   • 用户可控制同步范围
```

### 8.3 故障处理原则

```
✅ 推荐做法：

1. 自动切换
   • 主 Channel 故障自动切备用
   • 设置切换阈值
   • 记录切换日志

2. 故障通知
   • Channel 故障通知管理员
   • 提供故障详情
   • 建议处理方案

3. 恢复检测
   • 定期检测故障 Channel
   • 恢复后自动启用
   • 记录恢复时间

4. 日志记录
   • 记录所有 Channel 状态变化
   • 便于问题排查
   • 定期分析报告
```

## 9. 常见问题

### 9.1 Channel 连接失败

```
问题：某个 Channel 无法连接

可能原因：
1. 凭证过期或错误
2. 网络问题
3. API 限制
4. 服务宕机

解决方案：
- 检查凭证是否有效
- 检查网络连接
- 查看 API 限额
- 查看服务状态页面
- 查看错误日志
```

### 9.2 消息不同步

```
问题：多个 Channel 消息不一致

可能原因：
1. 同步配置错误
2. 发送失败
3. 格式不兼容
4. 时间延迟

解决方案：
- 检查同步配置
- 查看发送日志
- 调整消息格式
- 增加重试机制
```

### 9.3 消息重复

```
问题：收到重复消息

可能原因：
1. 去重配置未启用
2. 消息 ID 重复
3. 重试机制问题
4. 多实例运行

解决方案：
- 启用去重功能
- 检查消息 ID 生成
- 调整重试策略
- 确保单实例运行
```
