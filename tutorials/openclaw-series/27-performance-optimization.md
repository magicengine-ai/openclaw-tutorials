### 1.1 为什么需要性能优化？

```
┌─────────────────────────────────────────────────────────┐
│              性能优化的价值                              │
├─────────────────────────────────────────────────────────┤
│                                                         │

│  性能优化的好处：                                       │
│  ✅ 响应更快，用户体验好                                │

│  ✅ 并发能力强，支持多用户                              │
│  ✅ 系统稳定，减少故障                                  │
│                                                         │
│  典型优化场景：                                         │
│  • 减少 API 调用延迟                                     │
│  • 优化大文件处理                                       │

│  • 降低内存占用                                         │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

### 1.2 性能瓶颈分析

| 瓶颈类型 | 描述 | 表现 | 优化方向 |
|----------|------|------|----------|
| **网络延迟** | API 调用慢 | 响应时间长 | 缓存、CDN、就近接入 |
| **CPU 瓶颈** | 计算密集 | CPU 占用高 | 优化算法、异步处理 |
| **内存瓶颈** | 数据量大 | 内存占用高 | 流式处理、分页 |
| **IO 瓶颈** | 文件读写慢 | IO 等待长 | 缓存、异步 IO |
| **并发瓶颈** | 同时请求多 | 排队等待 | 连接池、限流 |

## 3. 缓存策略

### 3.1 什么是缓存？

```
缓存 = 存储常用结果，避免重复计算

场景示例：

没有缓存：
用户：北京今天天气怎么样？
  ↓
Agent: 调用天气 API → 返回结果

用户：（1 分钟后）北京天气如何？
  ↓
Agent: 再次调用天气 API → 返回结果（重复调用）

有缓存：
用户：北京今天天气怎么样？
  ↓
Agent: 调用天气 API → 返回结果 → 存入缓存

用户：（1 分钟后）北京天气如何？
  ↓
Agent: 从缓存读取 → 返回结果（无需调用 API）

好处：
• 减少 API 调用
• 加快响应速度
• 降低成本
```

### 3.2 缓存配置

```json
{
  "cache": {
    "enabled": true,
    "type": "memory",
    "ttl": 3600,
    "maxSize": 1000,
    "strategies": {
      "web_search": {
        "enabled": true,
        "ttl": 1800
      },
      "file_read": {
        "enabled": true,
        "ttl": 300
      },
      "api_call": {
        "enabled": true,
        "ttl": 3600
      }
    },
    "excludePatterns": [
      "*实时*",
      "*最新*",
      "*当前*"
    ]
  }
}
```

### 3.3 缓存策略对比

| 策略 | 描述 | 适用场景 | 优点 | 缺点 |
|------|------|----------|------|------|
| **内存缓存** | 存储在内存中 | 频繁访问的数据 | 速度快 | 重启丢失 |
| **文件缓存** | 存储到文件 | 持久化需求 | 重启保留 | 速度较慢 |
| **Redis 缓存** | 使用 Redis | 分布式场景 | 性能好、可共享 | 需要额外服务 |
| **智能缓存** | 根据访问频率 | 混合场景 | 自动优化 | 配置复杂 |

### 3.4 缓存失效策略

```
┌─────────────────────────────────────────────────────────┐
│              缓存失效策略                                │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  TTL（Time To Live）：                                  │
│  • 设置固定过期时间                                     │
│  • 简单、易实现                                         │
│  • 示例：天气数据缓存 30 分钟                            │
│                                                         │
│  LRU（Least Recently Used）：                           │
│  • 淘汰最久未使用的数据                                 │
│  • 适合内存有限的场景                                   │
│  • 示例：最多缓存 1000 条，超出淘汰最旧的                │
│                                                         │
│  条件失效：                                             │
│  • 根据数据特性决定                                     │
│  • 如：文件修改后失效                                   │
│  • 示例：文件内容变化后清除缓存                         │
│                                                         │
│  手动失效：                                             │
│  • 主动清除缓存                                         │
│  • 用于数据更新场景                                     │
│  • 示例：配置更新后清除相关缓存                         │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

## 5. 并发控制

### 5.1 什么是并发控制？

```
并发控制 = 管理同时进行的任务数量

场景：

没有并发控制：
10 个用户同时请求
  ↓
10 个任务同时执行
  ↓
CPU/内存过载
  ↓
响应变慢或失败

有并发控制：
10 个用户同时请求
  ↓
最多 5 个任务同时执行
  ↓
其他任务排队等待
  ↓
系统稳定，响应可预测
```

### 5.2 并发配置

```json
{
  "concurrency": {
    "maxConcurrent": 5,
    "maxConcurrentPerUser": 2,
    "queueSize": 100,
    "timeout": 60,
    "retryCount": 3,
    "backoff": {
      "enabled": true,
      "initialDelay": 1000,
      "maxDelay": 30000,
      "multiplier": 2
    }
  }
}
```

### 5.3 限流策略

| 策略 | 描述 | 适用场景 | 配置示例 |
|------|------|----------|----------|
| **固定窗口** | 固定时间内限制请求数 | 简单场景 | 100 请求/分钟 |
| **滑动窗口** | 滚动时间窗口限制 | 平滑限流 | 100 请求/滚动分钟 |
| **令牌桶** | 按速率产生令牌 | 突发流量 | 10 令牌/秒，桶容量 100 |
| **漏桶** | 固定速率处理 | 稳定输出 | 10 请求/秒处理 |

### 5.4 优先级队列

```json
{

        "weight": 10,

      "high": {
        "weight": 5,
        "maxConcurrent": 3
      },
      "normal": {
        "weight": 2,
        "maxConcurrent": 2
      },
      "low": {
        "weight": 1,
        "maxConcurrent": 1
      }
    },
    "defaultLevel": "normal"
  }
```

## 7. 优化实战

### 7.1 场景 1：减少 API 调用延迟

```
问题：API 调用经常超时

优化步骤：

1. 检查网络延迟
   ping api.example.com
   # 延迟 > 200ms 需要考虑优化

2. 选择就近的 API 端点
   {
     "model": {
       "endpoint": "https://api-cn.example.com"
     }
   }

3. 启用连接池
   {
     "connectionPool": {
       "enabled": true,
       "maxConnections": 10
     }
   }

4. 设置合理超时
   {
     "timeout": 30
   }

5. 添加重试机制
   {
     "retry": {
       "enabled": true,
       "maxRetries": 3,
       "backoff": "exponential"
     }
   }
```

### 7.2 场景 2：优化大文件处理

```
问题：处理大文件时内存占用高

优化步骤：

1. 限制文件大小
   {
     "file": {
       "maxFileSize": 10485760
     }
   }

2. 流式读取
   // 不要一次性读取
   const content = fs.readFileSync(file);  // ❌
   
   // 使用流式读取
   const stream = fs.createReadStream(file);  // ✅

3. 分块处理
   {
     "file": {
       "chunkSize": 1048576
     }
   }

4. 及时清理
   {
     "tempFile": {
       "cleanup": true,
       "cleanupDelay": 300
     }
   }
```
